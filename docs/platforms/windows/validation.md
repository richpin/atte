# Windows 미리보기 검증

현재 상태: **미리보기 검증 절차 준비, 실제 Windows 검증 대기**. Windows 11 x64 실행 결과와 Authenticode 코드 서명 수단은 아직 없다. 교차 빌드·테스트 컴파일은 실제 실행 결과가 아니다. 정식 Windows 지원은 선언하지 않는다.

## 배포 안내문

사용자가 [배포 절차](../../releases/windows.md)에 따라 prerelease 본문에 아래 안내를 복사하고 버전·커밋·다운로드 링크·SHA-256을 실제 산출물 값으로 채운다. 설치 파일 공개는 사용자가 직접 한다.

> Windows 11 x64용 미서명 미리보기입니다. Windows 실제 실행은 아직 검증하지 않았습니다. WSL·ARM64는 검증 대상이 아닙니다. Git for Windows와 인터넷 연결이 필요합니다. 설치 파일에는 Authenticode 게시자 서명이 없으며 SmartScreen 또는 조직 정책으로 차단될 수 있습니다. Tauri updater 서명은 업데이트 파일 무결성을 확인하는 별도 서명입니다. 보안 정책을 해제하지 말고 차단 메시지를 결과로 알려주세요. 중요한 원본 대신 별도 테스트 저장소에서 검증하세요.
>
> 버전 / develop 커밋: `<version> / <commit>`
> 다운로드: `<버전별 prerelease Setup.exe 링크>`
> SHA-256: `<SHA256SUMS의 값>`
>
> 설치·인증·대화·재개·파일/Git/worktree·웹 탭·단축키·알림·외부 앱·업데이트·저장 데이터 유지 모두 실제 검증 대기입니다. 오류는 아래 결과 양식에 환경과 재현 조건을 기록해 전달해 주세요. 인증 토큰·개인키·개인 대화와 파일 내용은 제외해 주세요.

## 실행 준비와 결과 규칙

Windows 11 x64 테스트 계정과 폐기 가능한 Git 저장소를 준비한다. 공백·한글·괄호·`&`가 포함된 경로도 만든다. 원본 데이터가 있으면 앱을 완전히 종료한 상태에서 앱 데이터와 작업 폴더를 별도 백업한다. 다운그레이드로 복원하지 않는다.

PowerShell에서 `Get-FileHash .\Atte_<version>_x64-setup.exe -Algorithm SHA256`를 실행해 배포한 SHA256SUMS와 비교한다. 다르면 설치하지 않는다. `winver`, WebView2 버전, `git --version`, 앱 버전·빌드 커밋, Claude·Codex 설치본 버전, 설치 경로와 권한을 기록한다.

각 검증 ID마다 `미실행 / 통과 / 실패 / 차단` 중 하나와 증거를 기록한다. 에이전트별 항목은 Claude와 Codex 각각 수행한다. 조건을 만들 수 없으면 통과 대신 차단 사유를 남긴다. 실패 수정 후 같은 환경·절차로 재검증하며 최초 실패 기록도 보존한다.

| ID | 절차와 통과 조건 |
| --- | --- |
| W01 설치 | 일반 사용자로 Setup.exe 설치 → Start Menu 실행. WebView2 초기화, 테마와 창 조작 확인. 설치 오류·보안 차단은 문구와 단계 기록. |
| W02 인증 | 각 에이전트 설치·로그인·대화. 브라우저/콘솔 인증 성공, 취소, 콘솔 직접 닫기, 로그인 중 앱 종료 후 재시도. 취소·실패가 성공으로 표시되지 않고 인증 자손이 남지 않아야 한다. |
| W03 작업 | 각 에이전트의 승인·질문 응답, 중지, 동시 스레드, 완전 종료 후 기존 맥락 재개. 에이전트 업데이트를 turn 중 요청해 완료 후 새 설치본으로 재실행되는지 확인. |
| W04 파일 | 특수문자 경로에서 파일 생성·편집·Ctrl+S·이동·휴지통·첨부·이미지·멘션. 외부 수정 충돌과 기존 대상 덮어쓰기 거부, junction 및 짧은 경로 별칭으로 보호 경계 우회 불가 확인. |
| W05 Git | 변경 조회·stage·commit·restore·stash. worktree 생성·공유, 한 스레드 삭제 시 보존, 마지막 스레드 삭제 시 정리, 앱 종료 시 보존. 테스트 변경만 사용한다. |
| W06 웹 | HTTPS와 로컬 서버, redirect·title·favicon·loading, 뒤/앞 이동·실패 탐색·popup, 탭 숨김·크기·포커스·스레드 전환·닫기. 원격 페이지의 앱 명령 호출, 앱 origin/file:/javascript: 이동·팝업, 다운로드가 거부되는지 확인. |
| W07 키 | 메인 UI와 웹 입력란 각각 Ctrl+T/W, Ctrl+Shift+W, Ctrl+Tab/Shift+Tab, Ctrl+1–9, Ctrl+F/S, Alt+F4. 웹 기본 편집 키 유지와 미저장 변경의 취소·저장 확인. |
| W08 알림 | 완료·승인·질문 알림, 배너/센터 클릭 → 창 복원·해당 스레드 이동. 집중 모드·시스템 차단, 확인·삭제·종료 뒤 제거와 웹 포커스 유지 확인. |
| W09 외부 앱 | Explorer, Other…의 exe 선택·취소, 특수문자 폴더가 단일 인수로 열리는지 확인. 사라진 폴더는 오류를 표시해야 한다. |
| W10 종료·복원 | 응답·인증 중 종료, 미저장 파일 종료 취소·저장, 설치/제거 중 종료 대기. 작업 관리자에서 해당 에이전트·인증 콘솔·자손 PID 소멸 확인. 재실행 후 메시지·첨부·설정·인증·worktree·관리 Node 설치본 재개 확인. |

세부 동작의 기준은 [Windows 작업 흐름](workflows.md), [알림](../../features/notifications.md), [파일](../../features/files.md), [worktree](../../features/worktrees.md)를 따른다.

## 두 버전 업데이트

같은 updater 키의 N과 더 높은 N+1을 [릴리스 절차](../../releases/windows.md)로 만든다. 버전별 URL은 보존하고, 실패 실험은 공개 채널 대신 별도 테스트 저장소의 prerelease endpoint를 주입한 테스트 빌드에서 한다. 정상 N+1 manifest와 파일을 보관하고 각 실험 후 복구한다.

| ID | 절차와 통과 조건 |
| --- | --- |
| U01 정상 확인 | N 설치 후 두 에이전트의 스레드·첨부·설정·worktree·미저장 파일 준비. 채널을 N+1로 바꾸고 시작 시/수동 확인에서 올바른 버전·진행률 표시 확인. |
| U02 재시도 | 다운로드 중 네트워크 끊기 → 오류 확인 → 연결 복구·다시 다운로드. 정상 파일 검증 후에만 재시작 가능해야 한다. |
| U03 거부 | 각각 정상 서명+변조 EXE, 정상 EXE+다른 키의 서명, 서명 버전과 manifest 버전 불일치를 제공. 모두 설치·재시작 없이 거부되어야 한다. 정상 manifest 복구 후 재시도 성공 확인. |
| U04 종료 취소 | 다운로드 후 재시작에서 미저장 확인 취소 → 앱·작업·다운로드 유지. 다시 승인 → 설치/제거 완료 대기, 인증·에이전트 자손 정리 후 설치 실행 확인. |
| U05 보존 | N+1 자동 재실행과 표시 버전 확인. W10의 저장 데이터 및 두 에이전트 맥락 재개를 N 상태와 비교. 앱 종료 후 다운로드 폐기·재다운로드도 별도로 확인. |
| U06 설치 실패 | 테스트 환경에서 설치 실행 실패 조건과 오류 기록. 기존 앱 재실행 → 정상 조건 복구 → 다시 업데이트 성공 확인. 재현할 수 없으면 차단으로 남긴다. |
| U07 채널 | macOS 정식 앱에서 Windows prerelease가 표시되지 않는지 확인. preview에서 stable로 자동 전환되지 않는지 확인. |

## 코드 서명과 정식 지원 판정

현재 서명 제공자·인증서 발급·계정 자격·키 보관·서명 도구 연결·서명 설치본 검증은 모두 **대기**다. [Tauri 공식 서명 절차](https://v2.tauri.app/distribute/sign/windows/)와 [Microsoft 서명 선택지](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)를 기준으로 사용자가 발급 가능한 Authenticode 인증서 또는 Artifact Signing을 선정한다. 발급·비용·계정 검증은 실제 계정으로 진행해야 한다.

서명 수단 확보 후 `bundle.windows.signCommand` 연결, 내부 atte.exe와 최종 Setup.exe 코드 서명, 신뢰 가능한 타임스탬프 확인을 수행한다. 최종 EXE에 updater 서명·SHA-256을 다시 생성한다. Windows PowerShell에서 두 파일 각각 `Get-AuthenticodeSignature <파일>`의 Status가 Valid이고 게시자가 발급 대상과 일치하는지 기록한다. 서명한 N→N+1으로 U01–U07을 다시 실행한다. 서명 유효성과 SmartScreen 표시 결과는 각각 기록한다. 코드 서명만으로 경고가 사라진다고 판정하지 않는다.

정식 지원은 W01–W10, U01–U07의 필수 검증 통과, 실패 수정 재검증, 서명 수단 확보와 서명 설치본 검증을 모두 완료한 뒤 사용자가 배포를 결정한다. 차단·미실행 항목이 있으면 실제 검증 대기 상태를 유지한다.

## 결과 양식

아래 양식을 실행별로 복사해 로컬 `.scratch/windows-support/results/`에 보관한다. 실제 결과를 받기 전에는 빈 양식을 성공 기록으로 취급하지 않는다. 확정된 동작·해결한 제한만 관련 docs에 반영한다.

```text
실행 일시 / 검증자:
Windows 버전·빌드 / x64 / 일반 사용자·관리자:
WebView2 / Git / Claude 설치본 / Codex 설치본 버전:
앱 N·N+1 버전 / develop 커밋 / 설치 파일 SHA-256 / endpoint:
설치 경로 / 작업 경로 / 보안·네트워크 조건:
코드 서명 상태 / 게시자 / 타임스탬프 / SmartScreen 표시:
검증 ID / 에이전트 / 결과(미실행·통과·실패·차단):
사전 조건 / 재현 단계 / 기대 결과 / 실제 결과:
오류 문구 / 로그·화면·PID 등 증거(비밀 제거):
업데이트 전후 데이터 비교:
실패 이슈 / 수정 커밋 / 재검증 결과:
```
