Status: ready-for-agent

# 스레드 삭제

## Problem Statement

Atte 사용자는 더 이상 필요하지 않은 스레드를 사이드바와 로컬 저장소에서 제거할 수 없다. ACP 에이전트가 `session/delete`를 지원하더라도 Atte에는 이를 호출하는 경로가 없고, 로컬 스레드·대기 메시지·목록 상태를 함께 정리하는 사용자 경험도 없다. 에이전트가 제거되었거나 인증·실행·원격 삭제에 실패하면 사용자가 해결할 수 없는 내부 사정 때문에 스레드를 정리하지 못하는 문제도 피해야 한다.

## Solution

모든 스레드에 삭제 기능을 제공한다. 사용자는 스레드 행을 우클릭하거나 행의 hover/focus 상태에서 나타나는 세로 말줄임표 버튼으로 같은 메뉴를 열고, 삭제 확인 창에서 작업을 확정한다.

확정하면 Atte가 소유한 스레드 정보와 대기 메시지를 먼저 삭제한다. 로컬 삭제가 성공하면 선택된 스레드는 즉시 닫고 빈 시작 화면을 표시한다. 원격 ACP 세션이 있으면 별도의 비동기 작업에서 에이전트의 삭제 capability를 확인한 뒤 `session/delete`를 best-effort로 요청한다. 원격 작업은 로컬 삭제를 지연시키거나 되돌리지 않으며, 실패는 진단 로그에만 남긴다.

## User Stories

1. Atte 사용자로서 스레드를 삭제하고 싶다. 그래야 더 이상 필요하지 않은 작업을 사이드바에서 정리할 수 있다.
2. Atte 사용자로서 스레드 행을 우클릭해 작업 메뉴를 열고 싶다. 그래야 목록에서 자연스럽게 삭제 작업을 찾을 수 있다.
3. Atte 사용자로서 스레드 행에 마우스를 올렸을 때 오른쪽 끝의 세로 말줄임표 버튼을 보고 싶다. 그래야 우클릭을 모르더라도 메뉴를 발견할 수 있다.
4. 키보드 사용자로서 스레드 행 또는 그 메뉴에 포커스가 있을 때 세로 말줄임표 버튼을 사용할 수 있기를 원한다. 그래야 포인터 없이도 삭제 확인 창을 열 수 있다.
5. Atte 사용자로서 우클릭과 세로 말줄임표 버튼이 동일한 메뉴를 열기를 원한다. 그래야 진입 방식에 따라 기능이 달라지지 않는다.
6. Atte 사용자로서 삭제 전에 확인 창을 보고 싶다. 그래야 실수로 스레드를 제거하지 않는다.
7. Atte 사용자로서 확인 창에서 삭제가 영구적이며 취소할 수 없음을 알고 싶다. 그래야 작업의 결과를 이해하고 결정할 수 있다.
8. Atte 사용자로서 확인 창을 취소하고 원래 스레드로 돌아가고 싶다. 그래야 삭제 의사를 바꿀 수 있다.
9. Atte 사용자로서 아직 ACP 세션이 없는 로컬 초안도 삭제하고 싶다. 그래야 한 번도 전송하지 않은 스레드를 정리할 수 있다.
10. Atte 사용자로서 에이전트가 ACP 세션 삭제를 지원하는지와 무관하게 삭제 메뉴를 사용하고 싶다. 그래야 프로토콜 capability가 로컬 정리를 막지 않는다.
11. Atte 사용자로서 에이전트가 제거된 스레드도 삭제하고 싶다. 그래야 더 이상 재개할 수 없는 항목이 목록에 남지 않는다.
12. Atte 사용자로서 에이전트 인증이 실패한 스레드도 삭제하고 싶다. 그래야 해결하기 어려운 인증 문제 때문에 목록 정리가 막히지 않는다.
13. Atte 사용자로서 에이전트 실행이 실패한 스레드도 삭제하고 싶다. 그래야 외부 프로세스 문제와 로컬 목록 관리를 분리할 수 있다.
14. Atte 사용자로서 원격 `session/delete`가 실패해도 로컬 스레드가 삭제되기를 원한다. 그래야 사용자가 처리할 수 없는 ACP 오류가 삭제를 방해하지 않는다.
15. Atte 사용자로서 원격 삭제 실패에 대한 별도 경고나 추가 선택을 받지 않기를 원한다. 그래야 내부 구현 세부사항 때문에 삭제 흐름이 복잡해지지 않는다.
16. Atte 사용자로서 실행 중인 스레드도 삭제하고 싶다. 그래야 먼저 작업을 수동으로 취소할 필요가 없다.
17. Atte 사용자로서 스레드 삭제가 현재 실행을 별도로 취소하지 않기를 원한다. 그래야 활성 세션 삭제의 구체적인 의미를 각 ACP 에이전트가 결정할 수 있다.
18. Atte 사용자로서 한 스레드를 삭제해도 같은 에이전트 프로세스를 공유하는 다른 스레드가 계속 동작하기를 원한다. 그래야 관련 없는 작업이 중단되지 않는다.
19. Atte 사용자로서 현재 보고 있는 스레드를 삭제하면 빈 시작 화면을 보고 싶다. 그래야 자동으로 다른 스레드에 입력하는 실수를 피할 수 있다.
20. Atte 사용자로서 보고 있지 않은 스레드를 삭제해도 현재 스레드가 유지되기를 원한다. 그래야 현재 작업의 맥락을 잃지 않는다.
21. Atte 사용자로서 삭제된 스레드가 늦은 ACP 이벤트나 비동기 명령 완료 때문에 다시 나타나지 않기를 원한다. 그래야 삭제 결과를 신뢰할 수 있다.
22. Atte 사용자로서 삭제된 스레드의 대기 메시지도 함께 제거되기를 원한다. 그래야 삭제된 작업의 미전송 입력이 남지 않는다.
23. Atte 사용자로서 앱을 다시 시작해도 삭제한 스레드가 복원되지 않기를 원한다. 그래야 삭제가 영속적으로 유지된다.
24. Atte 사용자로서 삭제 성공 toast를 받지 않기를 원한다. 그래야 목록에서 사라지는 직접적인 결과만으로 완료를 확인할 수 있다.
25. Atte 사용자로서 로컬 저장소 삭제가 진행되는 동안 중복 삭제를 실행할 수 없기를 원한다. 그래야 같은 작업이 중복 제출되지 않는다.
26. Atte 사용자로서 로컬 삭제에 실패하면 확인 창에서 오류와 재시도 가능성을 보고 싶다. 그래야 실제로 완료되지 않은 삭제만 조치할 수 있다.
27. Atte 사용자로서 로컬 삭제가 성공한 직후 확인 창이 닫히기를 원한다. 그래야 원격 정리 작업을 기다리지 않고 계속 사용할 수 있다.
28. Atte 사용자로서 원격 삭제 작업이 오래 걸려도 앱 사용이 막히지 않기를 원한다. 그래야 외부 에이전트의 응답성이 Atte UI에 영향을 주지 않는다.
29. Atte 사용자로서 삭제 메뉴와 확인 창이 스레드라는 일관된 용어를 사용하기를 원한다. 그래야 ACP 세션과 Atte 스레드를 혼동하지 않는다.
30. Atte 사용자로서 원격 세션이 남을 가능성을 관리하기 위한 복잡한 프로토콜 안내를 받지 않기를 원한다. 그래야 삭제 경험이 간결하게 유지된다.

## Implementation Decisions

- Atte 스레드와 ACP 세션은 별개의 식별자와 수명주기를 유지한다. 로컬 스레드는 사이드바 membership과 Atte 소유 상태의 기준이고, ACP 에이전트는 원격 세션 기록의 기준이다.
- 스레드 삭제의 사용자 계약은 로컬 삭제 완료를 기준으로 한다. 원격 세션 삭제는 로컬 삭제의 성공 조건이 아니다.
- 삭제 command는 로컬 저장소의 스레드 행과 그 행에 속한 대기 메시지를 제거한다. 별도의 schema migration이나 tombstone은 추가하지 않는다.
- 로컬 저장소 삭제가 실패하면 메모리 목록을 제거하지 않고 구조화된 오류를 반환한다. 사용자가 재시도할 수 있도록 확인 창을 유지한다.
- 로컬 저장소 삭제가 성공하면 인메모리 스레드 entry와 목록 entry를 제거하고 목록 구독자에게 새 목록을 발행한다. command는 이 로컬 결과가 확정된 뒤 성공한다.
- 원격 작업에 필요한 에이전트, 작업 폴더, ACP 세션 ID 정보는 로컬 entry 제거 전에 캡처한다.
- 원격 세션 ID가 없는 초안은 원격 작업 없이 로컬 삭제만 완료한다.
- 원격 세션 ID가 있으면 로컬 성공 뒤 detached 비동기 작업을 시작한다. 기존에 사용할 수 있는 공유 ACP 연결이 있으면 재사용하고, 없으면 해당 에이전트와 작업 폴더에 맞는 연결을 시작한다.
- 원격 삭제를 위해 기존 세션을 `load`하거나 `resume`하지 않는다. 연결 초기화에서 받은 현재 capability를 검사하고 `sessionCapabilities.delete`가 있을 때만 `session/delete`를 호출한다.
- 삭제 capability가 없거나 에이전트가 제거된 경우에는 원격 요청을 보내지 않고 작업을 정상 종료한다.
- 에이전트 시작, 초기화, 인증, capability 검사 또는 `session/delete`가 실패하면 민감한 payload를 노출하지 않는 진단 로그만 남긴다. 사용자 오류나 성공한 로컬 삭제의 rollback은 발생하지 않는다.
- 원격 삭제 작업에는 별도 timeout을 두지 않는다. 응답이나 연결 종료까지 백그라운드에서 기다리며 UI 수명주기와 분리한다.
- 활성 세션을 삭제하기 전에 `session/cancel`을 보내지 않는다. soft delete, hard delete, 활성 세션 거부 또는 허용은 ACP 에이전트가 결정한다.
- 삭제된 스레드의 원격 route와 로컬 update target을 분리하여 이후 도착하는 이벤트를 무시한다. 같은 프로세스와 연결을 공유하는 다른 스레드의 route와 실행은 유지한다.
- 원격 삭제의 성공 여부는 Tauri command 응답에 포함하지 않는다. frontend는 로컬 삭제 성공과 실패만 처리한다.
- 삭제 command는 좁은 application-level Tauri API로 제공한다. frontend에 DB나 ACP transport 세부 기능을 노출하지 않는다.
- 삭제 action은 모든 스레드에 제공한다. capability를 metadata에 저장하거나 메뉴 표시 조건으로 사용하지 않는다.
- 스레드 행은 선택 button과 메뉴 trigger가 중첩되지 않는 구조를 사용한다.
- Kobalte ContextMenu를 사용해 행 우클릭 메뉴를 제공하고, 같은 메뉴를 여는 별도의 세로 말줄임표 button을 행 오른쪽 끝에 둔다.
- 세로 말줄임표 button은 행의 hover 또는 focus-within 상태에서 나타난다. 별도의 `Shift+F10` 전용 처리나 새로운 전역 메뉴 추상화는 추가하지 않는다.
- 삭제 menu item은 위험 동작임을 시각적으로 구분하고, 선택하면 Kobalte AlertDialog 기반의 controlled 확인 창을 연다.
- 확인 창 제목은 `스레드를 삭제할까요?`, 설명은 `이 스레드가 영구적으로 삭제됩니다. 이 작업은 취소할 수 없습니다.`로 한다. 버튼은 `취소`와 위험 스타일의 `삭제`를 사용한다.
- 삭제 요청 중 확인 창을 유지하고 삭제 버튼의 중복 실행을 막는다. 로컬 성공 시 창을 닫고 별도 success toast를 표시하지 않는다.
- 로컬 삭제 실패는 확인 창 안의 접근 가능한 오류 영역에 표시한다. 원격 실패는 frontend로 전달하지 않는다.
- 선택된 스레드 삭제는 현재 view와 구독을 정리하고 선택을 비운다. 자동으로 다음 또는 최근 스레드를 선택하지 않는다.
- 선택되지 않은 스레드 삭제는 현재 선택과 작성 중 입력을 변경하지 않는다.
- 삭제가 시작된 view의 비동기 open, connect, send, subscription 등록 또는 update가 나중에 완료되어도 삭제된 스레드를 다시 선택하거나 목록에 추가하지 못하도록 기존 selection/view generation 경계를 사용한다.
- 앱이 개발 DB를 자동 초기화하는 코드는 추가하지 않는다. 호환이 필요 없는 기존 개발 DB는 개발자가 변경 적용 시 수동으로 한 번 삭제한다.
- `session/list` 자동 reconciliation은 도입하지 않는다. 미래의 명시적 Import 기능은 별도 설계로 다룬다.

## Testing Decisions

- 테스트는 private 채널, mutex 배치 또는 helper 호출 순서보다 사용자와 외부 프로토콜에서 관찰 가능한 결과를 검증한다.
- Rust의 주된 acceptance seam은 공개 Threads API와 실제 SQLite test store 및 ACP fixture의 조합이다. 이 seam 하나로 로컬 영속성, 목록 발행, 프로토콜 요청, 공유 연결 격리를 함께 검증한다.
- 로컬 초안을 삭제하면 목록과 `get`에서 사라지고, DB를 다시 열어도 복원되지 않으며, 대기 메시지도 남지 않는 테스트를 둔다.
- 목록 구독자가 스레드 제거가 반영된 전체 목록을 받는 테스트를 둔다.
- 원격 세션이 있는 스레드는 로컬 command가 성공한 뒤 fixture가 정확한 session ID의 `session/delete`를 받는 테스트를 둔다.
- ACP fixture에 delete capability 광고, 성공, 미지원, 오류, 지연 또는 연결 종료 동작을 표현할 수 있는 모드를 추가한다.
- delete capability가 없는 에이전트에는 `session/delete`를 보내지 않으면서 로컬 삭제가 완료되는 테스트를 둔다.
- 에이전트 제거, 실행 실패, 인증 실패와 원격 delete 오류에서도 로컬 삭제가 유지되는 테스트를 둔다.
- 실행 중인 스레드 삭제가 `session/cancel`을 보내지 않고 로컬에서 즉시 사라지는 테스트를 둔다.
- 공유 연결의 한 스레드를 삭제해도 다른 스레드가 계속 메시지를 보내고 업데이트를 받는 테스트를 둔다.
- 삭제된 스레드에 늦은 ACP update가 도착해도 목록이나 로컬 entry가 되살아나지 않는 테스트를 둔다.
- 원격 delete 응답이 오지 않아도 로컬 command와 UI가 완료되고, 앱 shutdown이 정의된 수명주기대로 동작하는 테스트를 둔다.
- 로컬 DB 삭제 실패 시 local entry와 목록이 유지되고 구조화된 오류가 반환되는 테스트를 둔다. 기존 storage failure 표현 방식을 재사용한다.
- frontend의 주된 acceptance seam은 렌더링된 앱과 mock Tauri command이다. 사용자가 보는 메뉴, dialog, 선택 결과와 오류를 이 seam에서 검증한다.
- 스레드 행 우클릭과 세로 말줄임표 button이 같은 메뉴를 열며, hover/focus 상태에서 button을 사용할 수 있는 테스트를 둔다.
- 메뉴의 삭제 항목이 정확한 확인 문구, 취소 button과 삭제 button을 가진 dialog를 여는 테스트를 둔다.
- 취소 시 command가 호출되지 않고 현재 선택이 유지되는 테스트를 둔다.
- 선택된 스레드 삭제 성공 시 command가 한 번 호출되고 dialog와 스레드 view가 닫히며 빈 시작 화면이 표시되는 테스트를 둔다.
- 선택되지 않은 스레드 삭제 성공 시 현재 스레드와 작성 중 입력이 유지되는 테스트를 둔다.
- 로컬 삭제 실패 시 dialog가 열린 채 접근 가능한 오류가 표시되고 재시도할 수 있는 테스트를 둔다.
- 원격 실패를 위한 frontend 상태나 toast가 없음을 사용자 관찰 결과로 검증한다.
- 늦은 비동기 command 완료와 subscription update가 삭제된 스레드를 되살리지 않는 동작은 기존 thread model의 view/selection race 테스트 seam에서 좁게 보강한다.
- 기존 Threads persistence 테스트, ACP fixture 기반 세션 격리 테스트, thread model 비동기 race 테스트, 앱 sidebar 테스트와 agent 삭제 AlertDialog를 prior art로 사용한다.
- Rust 테스트 이름은 동작과 조건이 드러나는 문장형 이름을 사용하고, 각 테스트는 가능한 한 하나의 사용자 관찰 결과를 설명한다.

## Out of Scope

- 스레드 보관, 보관 해제 또는 보관 목록 UI
- ACP `session/list`를 이용한 자동 동기화 또는 명시적 Import 기능
- 삭제 tombstone과 원격 세션 재등장 방지
- 원격 세션 삭제 성공 여부를 사용자에게 표시하는 UI
- ACP 에이전트가 수행하는 soft delete와 hard delete의 구분
- 삭제 뒤 `session/load` 가능 여부 확인
- 실행 중인 turn의 취소 또는 `session/close` 호출
- 에이전트 프로세스 전체 종료
- 삭제 취소, 휴지통 또는 복구 기능
- 사용자에게 원격 zombie 세션 관리 기능 제공
- 개발 DB 자동 초기화 또는 schema upgrade migration

## Further Notes

- ACP `session/delete`가 보장하는 것은 향후 `session/list` 결과에서 해당 세션을 제거하는 것이다. 실제 데이터 파기, 활성 세션 처리와 삭제 후 load 동작은 에이전트 구현에 달려 있다.
- 이미 없거나 존재하지 않았던 세션 삭제는 조용히 성공하는 것이 ACP의 권고 동작이다.
- Zed는 로컬 metadata를 먼저 삭제하고 원격 삭제를 detached best-effort 작업으로 수행하며, 연결과 RPC에 별도 timeout을 두지 않는다. Atte도 이 사용자 경험을 채택하되 ACP delete capability는 list capability와 독립적으로 검사한다.
- 미래에 명시적 session Import를 추가하면 원격 삭제에 실패한 세션이 다시 나타날 수 있다. 그 시점에 tombstone 또는 재등장 정책을 별도로 결정한다.
- 이 명세는 `Delete local threads before requesting ACP session deletion` ADR과 프로젝트 도메인 용어를 따른다.
