# 04: Registry 기반 ACP 에이전트 관리 시스템

**What to build:** 공식 ACP Registry의 목록과 배포 메타데이터를 바탕으로 에이전트를 발견·설치·인증하고, 설치된 에이전트로 스레드를 시작하는 공통 관리 시스템을 만든다. 지원하는 배포 형식의 새 에이전트가 Registry에 추가되면 Atte 코드 수정 없이 목록·설치·실행에 반영되어야 한다.

**Blocked by:** [03: 메시지 전송과 스트리밍 응답](./03-message-streaming.md)

Status: done

## 근거와 범위

부모 명세: [Atte 첫 버전 구현 명세](../spec.md). 관련 사용자 스토리: 1–7, 9–11, 41, 49–50.

기존 세 에이전트 대상 구현을 확장한다. Claude·Codex·Antigravity는 검증 사례이며 지원 대상의 고정 목록이 아니다. 기존 설치·저장·인증·스레드 통합을 유지하면서 Registry ID를 기준으로 공통 관리한다. 과거 완료 기록은 이전 범위의 증거이며 아래 확장된 완료 조건을 충족한 것으로 간주하지 않는다.

Zed의 고정 커밋 `b6171bcc982c406c34e786c09ae26f59620e52ae`에서 확인한 동적 Registry 목록, 플랫폼별 배포 선택, 배포 형식별 공통 설치기, 공통 NodeRuntime 및 실행 정의 방식을 채택한다. Zed의 제품별 설정·원격 실행·에이전트 이름별 인증 예외나 npm 버전 범위 정책까지 일괄 복제하지 않는다.

macOS 우선과 공통 ACP/capability 원칙을 유지한다. 지원 배포는 Zed 조사 시점의 binary와 npx다. uvx 등 미지원 배포는 이유를 표시하며 설치하지 않는다. 모든 Registry 항목의 인증된 실사용을 보증하지 않는다. 실계정 응답 검증은 Codex로 수행하며 나머지는 검증 범위를 명시한다.

설치 정보의 Rust 소유 SQLite 저장소와 마이그레이션을 확장하고 06의 스레드 저장 기반으로 유지한다. 저장된 스레드의 오프라인 열람은 06, 프로젝트 + 연결은 07의 책임이다. 사용자 승인·취소는 05에서 완성한다. 이번 범위에 자동 업데이트, 사용자 정의 Registry/실행 명령, 비-ACP 백엔드, 비-macOS 제품 지원은 포함하지 않는다.

## 설계 및 동작 계약

- 공식 Registry 전체를 읽고 ID·이름·설명·버전·배포를 데이터로 취급한다. 고정 TARGETS, 이름별 다운로드 URL, 에이전트별 설치 분기를 제거한다. 목록을 영속 캐시하고 시작 시 복원하며 Zed처럼 자동 갱신은 한 시간 간격으로 제한한다. 명시적 새로고침은 즉시 시도하고 실패 시 마지막 정상 목록과 설치 정보를 보존하며 오류를 표시한다.
- 현재 OS·CPU에 맞는 binary가 있으면 선택하고 없으면 npx를 선택한다. 선택한 binary 설치가 실패했다고 다른 배포로 조용히 전환하지 않는다. 플랫폼 또는 배포 형식이 미지원인 항목은 목록에서 이유를 표시하고 설치를 막는다.
- binary는 Registry의 archive/cmd/args/env와 선택적 sha256으로 처리한다. ZIP, tar.gz/tgz, tar.bz2/tbz2, raw executable을 공통 지원한다. 상대 실행 경로 및 공통 Node 명령 해석을 지원하며 에이전트별 경로 추측은 하지 않는다. 경로 이탈·압축 링크를 통한 탈출을 차단하고 다운로드·해제 크기를 제한한다. 제공된 체크섬 불일치는 설치 실패다.
- npx 배포는 앱 내부에 패키지를 설치하고 package executable을 찾아 공통 NodeRuntime으로 실행한다. Registry에 명시된 패키지 버전과 실제 설치 버전을 기록하며 이름별 패키지 매핑을 두지 않는다. 호환 가능한 시스템 Node/npm을 재사용할 수 있지만 없어도 OS·CPU별 관리형 Node를 앱 데이터에 다운로드해 동작해야 한다. 사용자의 전역 패키지나 셸 설정을 변경하지 않는다.
- 설치 산출물은 Registry ID·설치 경로·해석된 버전으로 관리하고 정상 설치가 있으면 재사용한다. 배포 비교용 installation_source를 저장하지 않으며 변경된 배포의 설치는 명시적인 삭제 후 설치로 수행한다. 부분 다운로드와 설치 실패를 성공으로 저장하지 않으며 이전 정상 설치를 보존한다. 런타임 준비와 설치 중복 실행을 조정한다. 최종 결과는 기존 공통 실행 정의(command/args/env)로 변환한다.
- 인증 방법·안내·실행은 ACP가 광고한 메타데이터와 capability로 결정한다. 에이전트 ID나 인증 방법 이름으로 API key 환경 변수·로그인 명령을 추측하지 않는다. 공통 지원 밖의 인증 방식은 미지원으로 안내한다. 메타데이터만으로 동작하지 않는 공급자 문제는 재현 근거와 제한으로 기록하고 정적 분기를 추가해 완료로 간주하지 않는다.
- 첫 제품 스키마는 agents 중심 v1이며 Registry ID를 그대로 사용한다. 개발 중의 짧은 ID 변환과 v2–v4 마이그레이션은 제품 코드에 포함하지 않는다. Registry에서 사라진 설치도 목록과 설치 상태를 보존하며 새 설치 가능 여부와 기존 실행 가능 여부를 구분한다.

## Acceptance criteria

- [x] 설치된 ACP를 확인 후 삭제할 수 있다. 해당 에이전트의 모든 연결·작업을 종료하고 설치 파일을 즉시 삭제한다. 스레드 내용은 유지하며 삭제 실패 시 설치 정보를 남겨 재시도한다. 공용 Node·로그인 정보·작업 폴더는 보존하고 실패·재시도를 표시한다.

- [x] Registry 전체 목록을 표시하고 현재 플랫폼의 설치 가능 여부와 이유를 보여준다. 새 ID의 항목을 Registry fixture에 추가하는 것만으로 UI 목록·설치·에이전트 선택에 반영되며 제품 코드의 이름별 수정이 필요 없다.
- [x] 목록 캐시의 재실행 복원, 갱신 성공·실패, 처음부터 오프라인인 상태, 미지원 배포 및 플랫폼, Registry에서 제거된 기존 설치를 구분한다. 목록 갱신 실패가 설치된 에이전트 사용을 막지 않는다.
- [x] 플랫폼 binary 우선/npx 대체 선택과 위 binary 형식들을 공통 처리한다. 잘못된 경로·손상된 다운로드·체크섬 불일치·설치 중단이 정상 설치를 훼손하거나 성공으로 기록되지 않는다.
- [x] Node/npm이 없는 환경에서도 관리형 런타임 준비 → npx 설치 → 공통 실행 정의 생성이 동작한다. 공통 NodeRuntime의 다운로드 실패·재시도·재사용을 검증하며 사용자에게 수동 설치나 실행 경로 입력을 요구하지 않는다.
- [x] 다운로드·런타임 준비·설치 진행, 성공, 실패와 재시도를 표시한다. 실제 산출물·해석된 버전과 Registry ID를 영속 저장하고 재실행 후 복원한다. 같은 설치 요청의 중복 실행과 부분 설치를 처리한다.
- [x] agents 중심 v1 초기화와 재실행에서 설치 정보·Registry 메타데이터를 보존한다. 개발용 v4 DB는 동일 스키마 확인·백업 후 버전 번호를 일회성으로 맞추며 앱에 과거 개발 스키마 변환 경로를 남기지 않는다.
- [x] 설치·ACP 연결·인증·실행 가능 상태를 구분한다. 세션 생성 성공이나 빈 authMethods만으로 인증 완료라고 판단하지 않으며 인증 만료 후 상태를 갱신한다.
- [x] 에이전트가 광고한 인증 방법을 공통 처리하고 실패 후 재시도할 수 있다. 기존 Codex 전용 사전 조건·안내 및 UI 분기를 제거한다. 자격 증명을 로그·스레드 기록에 출력하지 않는다. 미지원 인증은 성공으로 표시하지 않는다.
- [x] 설치된 실행 가능한 에이전트가 없으면 관리 화면으로 안내한다. 스레드 중 인증 오류에서도 관리 화면으로 이동하고 인증 후 명시적으로 같은 스레드를 재시도할 수 있다.
- [x] 설치 직후 재시작 없이 에이전트를 선택해 작업 폴더의 새 스레드를 만들고 자동 연결한다. 기존 스레드의 고정 실행·에이전트·구독은 목록 갱신, 관리 화면 이동 또는 다른 설치로 변경되거나 중단되지 않는다.
- [x] 공급자 이름과 임의의 인증 method ID에 의존하지 않는 모의 ACP 에이전트로 설치 → 인증 → 새 스레드 → 첫 응답·후속 응답의 공통 경로를 검증한다. binary/npx 설치와 저장 재구성은 제어 가능한 외부 경계에서 검증하고 기존 테스트를 유지한다.
- [x] 실제 macOS 앱에서 Registry 목록, binary 설치·실행 준비와 관리형 Node 기반 npx 설치를 확인한다. Codex로 인증 안내 → 폴더 선택 → 자동 연결 → 스트리밍·후속 응답 → 재실행 후 새 스레드를 확인한다. 그 밖의 에이전트는 설치·연결·실계정 응답의 검증 수준을 나누어 기록하고 미검증을 성공으로 표시하지 않는다.
- [x] 관련 frontend/Rust 검사와 production macOS 빌드를 통과한다. Standards/Spec 리뷰를 수행하고 확장된 범위의 검증 결과를 이 티켓의 Comments에 별도 날짜와 범위를 명시해 추가한다. 사용자의 별도 요청 없이 커밋하지 않는다.

#### 구현과 근거

- [공식 Registry](https://github.com/agentclientprotocol/registry/blob/main/README.md)의 stable CDN index를 사용한다. [배포 규격](https://github.com/agentclientprotocol/registry/blob/main/FORMAT.md)에 따라 npm 패키지와 현재 macOS 플랫폼의 zip 바이너리를 선택한다. Antigravity의 macOS Intel 배포가 없으면 지원하지 않는 것으로 표시한다.
- `b591a6e`의 관리 화면 분리·고정 에이전트·스레드 유지 패턴과 `65023dc`의 실제 ACP 관찰을 적용했다. 관리 화면 이동은 스레드의 프로세스나 구독을 재생성하지 않는다. 설치 정의 교체도 이미 생성된 스레드의 실행 정의를 바꾸지 않는다.
- 저장 라이브러리가 기존 의존성에 없음을 확인했다. [rusqlite 0.40.2](https://docs.rs/crate/rusqlite/0.40.2)는 현재 유지보수되는 SQLite 래퍼이며, 작은 Rust 저장소에 ORM/별도 런타임 없이 트랜잭션과 스키마 마이그레이션을 제공한다. bundled SQLite를 사용하고 `Store`에서 `user_version` 0→1 마이그레이션을 트랜잭션으로 실행한다. 이번 스키마에는 설치 정보만 포함한다. 기존 reqwest 0.13.5를 직접 재사용한다.
- 설치 디렉터리는 앱 데이터 폴더 아래에서 설치마다 고유하게 생성한다. npm은 Registry의 고정 버전과 실제 package.json 버전을 비교하고 로컬 엔트리포인트를 저장한다. 바이너리는 플랫폼 배포 버전과 추출된 경로를 저장하며, Registry가 제공한 SHA-256이 있으면 검사한다. 실패는 설치 성공으로 저장하지 않는다.
- 인증 방식은 [ACP SDK의 안정 v1 타입](https://docs.rs/agent-client-protocol/2.1.0/agent_client_protocol/)과 [Registry 인증 규약](https://github.com/agentclientprotocol/registry/blob/main/AUTHENTICATION.md)을 따른다. Agent 방식은 `authenticate`, Terminal 방식은 제공된 추가 인수·환경으로 macOS Terminal에서 실행하며 종료 코드로 결과를 확인한다. 자격 증명은 UI 스레드·앱 로그·설치 DB에 저장하지 않는다.
- Codex `api-key` 호환 안내는 설치된 1.12.0 어댑터의 `CODEX_API_KEY` / `OPENAI_API_KEY` 요구사항을 근거로 한다. 새 키 입력 UI는 추가하지 않는다. 환경 변수가 없는 경우 해결 가능한 안내와 ChatGPT 선택 경로를 제공한다.
- 초기화 성공·세션 생성·빈 인증 방식은 인증 완료의 근거로 사용하지 않는다. 인증 성공 응답 또는 실제 prompt 성공이 인증 근거다. 스레드의 인증 만료는 관리 화면에도 반영하며, 로그인 성공만으로 실패한 스레드를 자동 재시도하지 않는다.

### 확장 범위 구현·검증 — 2026-09-17

Registry 기반 공통 에이전트 관리 범위를 구현했다. 기존 세 에이전트 검증 기록과 구분한다.

- 고정 TARGETS를 제거하고 Registry ID·이름·설명·배포를 사용한다. SQLite v2에 정상 목록과 갱신 시각을 보존하며 자동 갱신 시도는 한 시간으로 제한한다. 명시적 새로고침은 즉시 시도하고 실패해도 캐시와 기존 설치를 유지한다. 기존 짧은 ID는 v1→v2 트랜잭션에서만 변환한다.
- 플랫폼 binary 우선, 해당 플랫폼 binary가 없을 때 npx를 선택한다. 미지원 압축·설치 형식과 uvx는 이유를 표시하고 설치를 차단한다. binary 실패 후 npx로 전환하지 않는다. ZIP/tar.gz/tgz/tar.bz2/tbz2/raw를 처리하고 경로 이탈·링크·중복 파일을 거부한다. 다운로드 1 GiB, 해제 2 GiB, 엔트리 100,000개 제한과 선택적 SHA-256 검증을 적용한다.
- 설치마다 별도 산출물을 유지하며 실패·취소 시 임시 디렉터리를 정리한다. 이전 정상 설치와 실행 중인 스레드는 보존한다. Registry 버전·선택 배포·명시 패키지 버전으로 재사용 여부를 판단하고 실제 해석 버전을 별도 저장한다. 환경 변수의 정렬 순서는 재사용 키에 영향을 주지 않는다.
- Node는 에이전트 공통 관리형 런타임을 사용한다. 시스템 Node 재사용은 필수가 아닌 선택 사항이므로 이번 구현에는 넣지 않았다. 공식 Node v24.21.0 macOS arm64/x64 tar.gz와 고정 SHA-256을 사용하고 준비 작업을 직렬화한다. npm은 앱 내부에서 실행하며 사용자 전역 패키지나 셸 설정을 변경하지 않는다. npm lifecycle script는 실행하지 않는다.
- 인증 이름·ID별 추측을 제거했다. ACP Agent/Terminal 방식과 공급자의 설명을 사용한다. SDK 1.7의 알 수 없는 auth type→Agent fallback을 발견하여 initialize 원본 discriminator를 보존·검사한다. 미지원 방식은 UI와 실행 양쪽에서 차단한다. Terminal 인수·환경은 사용 중인 stable v1 SDK의 append/override 계약을 따른다.
- Solid resource는 캐시를 먼저 보여주고 ID 기준으로 reconcile하여 갱신 중에도 항목과 버튼의 정체성을 유지한다.

### Registry 아이콘 표시 — 2026-09-17

사용자 추가 요청으로 Registry의 선택적 `icon` URL을 캐시·카탈로그 응답에 보존하고 에이전트 관리 화면의 이름 옆에 표시한다. 기존 캐시에 아이콘 필드가 없어도 읽을 수 있으며 목록 새로고침으로 최신 아이콘을 받는다. Kobalte Image로 로딩 중·누락·실패 시 기본 터미널 아이콘을 표시한다. 외부 이미지는 공식 Registry CDN만 CSP에서 허용하며 SVG를 이미지로 표시하고 DOM에 삽입하지 않는다. 이미지 파일의 별도 오프라인 저장은 추가하지 않는다.

검증 완료: UI 22개·Rust 45개 통과(기존 opt-in smoke 2개 제외), Biome/FSD/typecheck와 Rust fmt/check/Clippy 통과, production macOS 번들 빌드 통과. 재실행 후 아이콘 URL 보존과 선택 필드 누락 호환, 이미지 성공·실패·누락의 UI 표시를 검증했다. 실제 macOS 앱에서 목록 새로고침 후 기본 아이콘이 Agoragentic·Amp의 공식 아이콘으로 바뀌는 것을 확인했다. Standards/Spec 리뷰 지적 각각 0개.

### agents 중심 저장과 즉시 삭제 — 2026-09-17

사용자 요청에 따라 기존 지연 삭제·배포 비교 정책을 대체한다. `agents`에 에이전트당 한 행으로 Registry 메타데이터와 설치 정보를 저장하고, 갱신 시각만 `app_metadata`에 보관한다. 기존 installations·registry_cache·pending_removals 테이블과 installation_source를 제거한다. 정상 설치는 그대로 사용하며 다른 배포로 바꾸려면 삭제 후 설치한다.

삭제는 선택 해제와 해당 에이전트 연결 종료 → 프로세스 회수 → 파일 삭제 → 설치 컬럼 비우기 순서다. 오류 시 설치 정보를 보존하여 삭제 재시도를 허용한다. 스레드 내용·다른 에이전트·작업 폴더·공용 런타임·로그인 정보는 유지한다. 삭제된 설치를 사용했던 스레드는 다시 연결하지 않으며 재설치 후 새 스레드를 만든다. v3의 남은 삭제 대기 파일은 마이그레이션에서 정리한 뒤 테이블을 제거한다. 상세 구조와 복구 규칙은 [DB 구조](../../../docs/database.md)에 기록한다.

검증: UI 23개·Rust 50개 통과(기존 opt-in smoke 2개 제외). v1/v3 마이그레이션과 재진입, Registry 갱신 중 설치 보존, 즉시 삭제·재설치, 삭제 실패 후 재시도, 실행 중 스레드 중단과 다른 에이전트 보존을 검사했다. 종료와 삭제 경합에 대한 Standards 지적 1개를 공통 종료 잠금과 회귀 테스트로 해결했으며 재리뷰 Standards/Spec 지적 각각 0개다. 현재 구조는 `docs/database.md`에 문서화했다.

Production macOS 빌드와 커밋 전 전체 검사도 통과했다. 실제 로컬 DB는 확인 시점에 이미 v4였으며 agents 41행·설치 3건을 확인하고 현재 상태를 백업했다. 최종 앱 재실행 후 같은 설치 3건 복원과 새 삭제 확인 문구·취소를 확인했다. 실제 사용자 설치는 삭제하지 않았으며 즉시 삭제·재설치와 프로세스 종료는 테스트용 ACP로 검증했다.

### 초기 스키마 v1 확정 — 2026-09-18

사용자 요청으로 agents 중심 구조를 첫 스키마 v1으로 확정한다. 001_agents.sql 하나로 초기화하며 이전 개발용 v1–v4 변환 SQL과 정리 코드를 제거했다. 위 마이그레이션 기록은 개발 중 이력이며 현재 제품 계약은 이 항목과 docs/database.md를 따른다. Registry 새로고침은 registry_metadata와 전체 갱신 시각만 트랜잭션으로 바꾸며 launch_definition·installed_version·artifact_path는 보존한다. 실행 정의는 실제 설치 성공 시 기록하고 삭제 성공 시 비운다.

검증: Rust 49개 통과(기존 opt-in smoke 2개 제외), fmt/check/Clippy 통과. 기존 로컬 DB는 새 v1과 테이블 정의가 동일함을 확인한 뒤 백업하고 user_version만 4→1로 변경했다. 변경 전후 agents·app_metadata 전체 데이터 해시가 동일했다. Standards/Spec 리뷰 지적 각각 0개.
Production macOS 빌드 및 v1 DB로 최종 앱 시작에 성공했고 기존 설치 3건이 관리 화면에 복원됨을 확인했다.
